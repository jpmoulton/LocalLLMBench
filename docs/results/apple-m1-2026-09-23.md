# Measured: Apple M1 (8 GB), native Metal runtime, 2026-09-23

The first live runs of the `metal-native` runtime. They show that the runtime works end to end on a small Mac and
what it measured there; they are **screening evidence, not validated presets**. The raw run directories are local
(`runs/mac/`, ignored by Git). The three candidate tables below are the output of

```bash
python scripts/native_results_summary.py <run directories>
```

over the directories each heading names, and every candidate's machine-readable row is in
[apple-m1-2026-09-23.json](apple-m1-2026-09-23.json). The coding-suite table and the verified-context table are
assembled by hand from those rows and the raw evidence they point to.

## Admission settings that differ from the packaged defaults

`native_limits.memory_reserve_mib` was **512** for the two-model sweep and **0** for the context, 2K and coding
sessions; both values are part of every candidate's fingerprint. The default (1024) refused the first live candidate
twice, with 1197 MiB and then 2025 MiB available against the 2080 MiB it required. With 0, admission still requires
the model file's size in available memory. The watchdog stayed the in-run guard (server footprint against the Metal
working set, host swap growth over 2 GiB, critical pressure) and recorded no violation in any candidate. Read every
speed below with the swap growth beside it.

### Interruption and resume, live

A two-candidate 2K session (Qwen3-1.7B, f16 then q8_0 KV; `runs/mac/resume-tests/`) was started the way a terminal
runs it and sent SIGINT about 15 s into its first candidate's evaluation, with llama-server serving. The candidate
was recorded as `cancelled` at the `quality` stage; the server stopped on SIGTERM (`returncode=0`), cleanup proved it
absent, the lease was released, and `tune` exited 3 with the resume command. `llmbench resume` then ran the
interrupted baseline again and the remaining candidate; the session finished `complete` with no llama-server left.
(A first attempt launched the session as a background job of a non-interactive shell, which starts it with SIGINT
ignored; that run simply completed and is not counted as an interruption test.)

## How to read these numbers

* **Speed** is the server's own generation rate over a 512-token completion after a filled prompt of the
  candidate's size (median of three, with the range). Prefill is the server's prompt rate for those prompts, and
  "first token" includes that prefill. The same Qwen3-1.7B 4K baseline measured 27.2, 24.6 and 27.3 tok/s in three
  sessions (host swap growth 889, 1505 and 1238 MiB), and Qwen3.5-2B's 28.9-30.0: differences of a few percent
  between candidates are within what a repeat shows here. No candidate met the packaged 50 tok/s speed floor, which
  is one of several reasons (with `holdout_unverified` and an absolute-quality floor in every case) each candidate
  is marked not eligible.
* **Memory** is unified memory: the server's `phys_footprint` after load and at its peak during evaluation (it
  includes the Metal buffers), the Metal buffers the server logged, and host swap growth (host-wide, other
  applications included). It is never VRAM. Process RSS understated the same server by about 3x (618 vs 1901 MiB in
  the first smoke run).
* **Quality** is per suite, on small item counts that resolve only large differences. BFCL ranged from 10/21 to
  17/21 across all candidates; with 21 items a difference of a few items is noise, and no paired test was run, so no
  setting or model has a demonstrated quality advantage here. In `x/n`, `n` counts every item the model was
  evaluated on, including items whose response was cut off (those score 0 in `x`); harness errors are listed
  separately and never scored.
* **Cut off** means a response hit the 512-token output cap, which is not a wrong answer; temperature 0 with 512
  output tokens is unfair to reasoning modes. With reasoning on, both models spent the cap thinking on RULER (2/2),
  on BFCL (7 and 3 items) and on the local fixtures (4 of 9 and 6 of 11 responses; for Qwen3.5-2B all six NIAH
  answers), which is why their NIAH and tool-fixture cells are low; the last column counts those responses.
* **NIAH strict (lenient)**: the local needle fixtures require an exact JSON protocol. With reasoning off and an f16
  or q8_0 cache, Qwen3-1.7B found every needle at 4K (lenient 6/6) but wrapped its answers in a Markdown code fence,
  which the strict scorer rejects (the project reports both, never one instead of the other).

## What went wrong, and what it means

* **Most Qwen3-1.7B candidates in sessions that include RULER make no context claim.** RULER's `niah_multikey_3`
  haystack is built from whole key-value lines of UUIDs (about 75 tokens each), and the generator never accepts a
  prompt over its target. With Qwen3-1.7B's template in non-reasoning mode, 51 lines give 4023 tokens and a 52nd
  would overshoot 4096 (by about one token, estimated from the reasoning-on prompt), so the prompt lands 73 tokens short, outside the ±64 tolerance. The harness records that
  item as `environment_error` and, correctly, withholds the candidate's context claim; the reasoning-on template is
  different and its prompt fit (4093 tokens), so that candidate is context-verified. Everything else was verified
  per sample: at the 8960 allocation the three speed probes held 8182-token prompts and the six local NIAH prompts
  8184-8192 tokens. The fix belongs in the RULER generator (finer haystack units or a wider tolerance) and would
  change prompts for the NVIDIA runtime too, so it was not made here.
* **Qwen3-1.7B with a `q4_0` KV cache has no accepted speed figure.** The server generated all 512 tokens of each
  probe (its own log reports 28.8, 28.3 and 27.8 tok/s), but each stream stalled for about 11 s after about 190
  chunks and ended in an error event (code 500, "The model produced output that does not match the expected
  peg-native format"): the pinned server's chat-output parser rejected the continuation. Without a completed stream
  the harness has no verified speed observation and records the speed as unmeasured, not zero. The candidate's
  quality benchmarks ran normally. f16 and q8_0 produced parseable output on the same prompt.
* **Qwen3.5-2B with a `q8_0` KV cache measured 25.3 tok/s against 29.3 for f16 in the same sweep**, 14% lower with
  non-overlapping ranges (25.1-25.8 vs 28.8-30.3), while its footprint was lower as expected. It was measured once;
  whether it repeats is open.

## Not measured

* Partial GPU offload, KV in system RAM and batch/ubatch variations are implemented and selectable but were not
  swept here; neither were the 5888 and 7168 allocations.
* No holdout ran: no candidate passed the packaged acceptance policy, so nothing here is a validated preset.
* NVIDIA was not run live on this machine; the NVIDIA runtime's behaviour is covered by the unit suite only.
