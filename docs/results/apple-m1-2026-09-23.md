# Measured: Apple M1 (8 GB), native Metal runtime, 2026-09-23

The first live runs of the `metal-native` runtime. They show that the runtime works end to end on a small Mac and
what it measured there; they are **screening evidence, not validated presets**. The raw run directories are local
(`runs/mac/`, ignored by Git); every table below is regenerated from them with

```bash
python scripts/native_results_summary.py runs/mac/sweep-main runs/mac/sessions --json results.json --markdown results.md
```

and the machine-readable rows are in [apple-m1-2026-09-23.json](apple-m1-2026-09-23.json).

## Admission settings that differ from the packaged defaults

`native_limits.memory_reserve_mib` was **512** for the two-model sweep and **0** for the context, 2K and coding
sessions, and both values are part of every candidate's fingerprint. The default (1024) refused the first live
candidate twice: the host had 1.2-2.0 GB available beside the owner's applications against the 2.1 GB the default
asked for. With 0, admission still requires the model file's size in available memory; the watchdog stayed the
in-run guard (server footprint against the Metal working set, host swap growth over 2 GiB, critical pressure) and
never fired. Read every speed below with the swap growth beside it.

### Coding suites

Both models, one baseline candidate each (4096 usable input, f16 KV, reasoning off), in a separate session with
the sandbox up: a 1 GiB Colima VM (2 vCPU) running the calibrated `linux/arm64` worker, each case in its own
container (no network, read-only root, no capabilities, 512 MiB, 1 CPU, 64 pids). Before these sessions the worker
was calibrated again at this VM size: worker acceptance passed, all 83 Aider Polyglot references passed and all 83
stubs failed. Items: the three private coding fixtures, the first 10 EvalPlus MBPP+ items of the seeded development
order, and the first 4 Aider Polyglot Python development exercises (two attempts each). Generated code never ran
on the host.

|---|---|---|---|---|---:|---:|---|---|
| Qwen3-1.7B | 3/3 | 4/10 | 0/4 (all refused by the edit parser; 0 of 8 responses cut off at 512 tokens) | 27.3 | 1927 | 1238 | yes | yes |

The two models failed Aider's SEARCH/REPLACE edit format in different ways. Qwen3-1.7B's responses all finished
normally but opened each edit block with a bare `<<<<<<<` instead of `<<<<<<< SEARCH`, on both attempts, so the
parser refused them and no test ran: that is the model's result. Qwen3.5-2B wrote the markers correctly but left out
the file name or prefixed it with the format example's `path/to/` directory (the prompt shows `path/to/file.ext`),
and 6 of its 8 responses were cut off by the 512-token output cap (the packaged default on both runtimes); by the project's rule a cut-off response is not a
wrong answer, so its 0/4 says more about the output cap than about the model. Ten EvalPlus items and four exercises
resolve only very large differences: these numbers show the sandboxed coding path working on the Mac, not the
models' coding ability.

### Interruption and resume, live

A two-candidate 2K session (Qwen3-1.7B, f16 then q8_0 KV) was started the way a terminal runs it and sent SIGINT
about 15 s into its first candidate's evaluation, with llama-server serving. The candidate was recorded as
`cancelled` at the `quality` stage; the server stopped on SIGTERM (`returncode=0`), cleanup proved it absent, the
lease was released, and `tune` exited 3 with the resume command. `llmbench resume` then ran the interrupted baseline
again and the remaining candidate; the session finished `complete` with no llama-server left. (A first attempt at
this test launched the session as a background job of a non-interactive shell, which starts it with SIGINT ignored;
that run simply completed, and is not counted as an interruption test.)

## How to read these numbers

* **Speed** is the server's own generation rate over a 512-token completion after a filled prompt of the
  candidate's size (median of three, with the range). Prefill is the server's prompt rate for those prompts, and
  "first token" includes that prefill. The same Qwen3-1.7B baseline measured 27.2 and 24.6 tok/s on two runs an hour
  apart with 889 and 1505 MiB of host swap growth: on this machine the host's memory state moves speed by about 10%,
  so differences of that size between candidates are not findings. Nothing here meets the packaged speed floor of
  50 tok/s, which was set on an RTX 5090; that is why every candidate is "not eligible", not a defect.
* **Memory** is unified memory: the server's `phys_footprint` after load and at its peak during evaluation (it
  includes the Metal buffers), the Metal buffers the server logged, and host swap growth (host-wide, other
  applications included). It is never VRAM. Process RSS understated the same server by 3x (618 vs 1901 MiB).
* **Quality** is per suite, on small item counts that resolve only large differences. BFCL ranged from 10/21 to
  17/21 across all candidates; with 21 items a difference of a few items is noise, and no paired test was run, so no
  setting or model has a demonstrated quality advantage here. `x/n` counts only items the model was evaluated on; a
  harness error is listed beside it and never scored.
* **NIAH strict (lenient)**: the local needle fixtures require an exact JSON protocol. Qwen3-1.7B found every needle
  at 4K (lenient 6/6) but wrapped its answers in a Markdown code fence, which the strict scorer rejects (the
  project's LIVE-004 rule reports both, never one instead of the other).
* **Cut off** means the response hit the 512-token output cap. With reasoning on, both models spent the cap
  thinking on RULER (2/2 cut off) and on several BFCL items; those are not wrong answers, and temperature 0 with
  512 output tokens is unfair to reasoning modes.

## What went wrong, and what it means

* **Qwen3-1.7B makes no context claim at 4K or 8K.** RULER's `niah_multikey_3` haystack is built from whole
  key-value lines of UUIDs (about 70 tokens each); for this tokenizer and seed the closest prompt the generator can
  build is 4023 tokens against a 4096 target, outside its ±64 tolerance. The harness records that item as
  `environment_error` and, correctly, withholds the candidate's context claim. Everything else at those sizes was
  verified per sample: at the 8960 allocation the three speed probes held 8182-token prompts and the six local NIAH
  prompts 8184-8192 tokens. The fix belongs in the RULER generator (finer haystack units or a wider tolerance) and
  would change prompts for the NVIDIA runtime too, so it was not made here.
* **Qwen3-1.7B with a `q4_0` KV cache has no speed figure.** Each 512-token `ignore_eos` probe ended in HTTP 500
  from the pinned server: "The model produced output that does not match the expected peg-native format" (its chat
  output parser rejected the continuation). The harness recorded the speed as unmeasured, not zero; the candidate's
  quality benchmarks ran normally. f16 and q8_0 produced parseable output on the same prompt.
* **Qwen3.5-2B `q8_0` KV measured 25.3 tok/s against 29.3 for f16** in the same session; its footprint was lower as
  expected. On three repetitions under host memory pressure this is within the run-to-run spread above.

| Model | Largest allocation with the candidate's context verified | Prompts actually held | Speed there |

| Qwen3.5-2B | 17152 (16384 usable input) | speed probes 16374 tokens, local NIAH 16376-16384 tokens (5/6 strict), RULER 4096 | 27.1 tok/s, 434 tok/s prefill, 37.8 s to first token |

Qwen3.5-2B's hybrid attention keeps its KV cache small (57 MiB at 4K, 6 of 24 layers), so 16K cost about 190 MiB
more peak footprint than 4K; Qwen3-1.7B's Metal buffers grew by 465 MiB from 4K to 8K (its f16 cache covers all 28
layers) and its peak footprint by about 460 MiB.

## Not measured

* Partial GPU offload, KV in system RAM and batch/ubatch variations were implemented and are selectable, but were
  not swept in this session.
* No holdout ran: no candidate passed the packaged acceptance policy, so nothing here is a validated preset.
* NVIDIA was not run live on this machine; the NVIDIA runtime's behaviour is covered by the unit suite only.
